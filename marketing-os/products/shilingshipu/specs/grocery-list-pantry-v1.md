## 为什么三件事一起改

它们共用同一份数据：**`checked` 状态是"已买"的唯一真相来源**，它同时喂三个出口。分三次改会把同一段逻辑写三遍。

```
                    ┌─→ 复制清单（三种范围）
item.checked ───────┼─→ 进度条 / CTA 状态机
                    └─→ 盘一盘（自动带入）→ 库存（家里还有的）
```

---

## 一、Bug 修复：复制清单在全勾时复制出空内容

### 现象
所有项勾选后（进度 100%），点「复制清单」，粘贴出来是空的。屏幕上明明列着 17 样。

### 推断的成因
```js
const text = items.filter(i => !i.checked).map(...).join('\n')
```
过滤"未勾选 = 还要买的"，全勾之后是空数组。**逻辑本身讲得通，问题是静默失败** —— 没有任何反馈，用户以为功能坏了。这类"我做了但什么都没发生"最伤信任。

### 修复

**R1（必须）· 永不静默复制空内容。**
任何复制路径，若最终文本为空，不写剪贴板，改为提示：
> 都买齐了，没有待买的。要复制全部清单吗？ [复制全部]

**R2（必须）· 复制范围可选。**
点「复制清单」弹出轻量选择（不要做成整页弹窗）：

| 选项 | 内容 | 数字 |
|---|---|---|
| 待买的 | `checked === false` | 实时计数 |
| 全部 | 所有项 | 实时计数 |
| **已买的** | `checked === true` | 实时计数 |

计数为 0 的选项置灰，不可点。

**R3（必须）· 所见即所得的格式。**
保持屏幕上的分区和顺序。已买项带 `✓`。有 tag 的带上（例：`亚超`）。

```
买菜清单 · 处暑 8/24

【蔬菜区】
✓ 葱
✓ 番茄
✓ 莲藕（亚超）
✓ 南瓜

【肉蛋区】
✓ 排骨
  鸡蛋
```

**R4** · 剪贴板写入失败时（iOS Safari 需用户手势、无 HTTPS 等）不要静默失败，降级为展示一段可长按选中的纯文本。

### 顺带
`蔬菜区 (0)` 这个计数当前读起来像坏了 —— 下面明明列着四样。改成 `蔬菜区 (0/4)` 或 `蔬菜区 · 已齐`。

## 二、CTA 状态机：清单齐了以后，主按钮要换

### 问题
进度 100%、文案已经说「齐了，回家做饭。」，但最显眼的按钮还是「复制清单」。用户此刻真正要做的是回家做饭 / 盘一盘，不是再复制一遍购物清单。

### 规则

| 进度 | 主 CTA | 次级 |
|---|---|---|
| 0% | 从餐桌导入 / 快速添加 | — |
| 1–99% | **复制清单（待买的）** | 清空、按菜品/按超市分区 |
| 100% | **盘一盘 →** | 复制清单（降为图标或文字链） |

**同时**：100% 时那条「齐了，回家做饭。」从静态文案变成可点的入口，点进去 = 盘一盘。它现在是页面上最醒目的一行字，却不可点，是浪费。

### 边界
- 清单为空（0 项）时不显示进度条，也不显示 100%。空清单不是"齐了"。
- 用户手动取消勾选导致从 100% 掉回 99%，CTA 要跟着退回。用状态推导，不要用一次性的事件触发。

## 三、盘一盘：自动带入 + 库存

### 现在的形态
「买回来的菜」是一个空输入框，用户从零手打。但系统已经知道他买了什么了 —— 勾选状态就是最好的证据，而且比回忆准。

### 改成三段

```
盘一盘
├ 这次买的        ← 自动带入 checked=true，每项可删
├ 家里还有的      ← 库存活跃项，默认折叠，可勾回来
├ 还买了别的      ← 手动 / 语音补
└ 清单上还有 3 样没勾：芹菜、豆腐、香菇  ＋     ← 折叠一行
```

### 三条关键规则

**S1 · 自动带入，但每一项都必须可删。**
不能只读。买了当天就吃掉的、买错的、勾错的，要能一下划掉。第一次不准就没有第二次。

**S2 · 没勾的折叠成一行，不要彻底消失。**
「不需要 / 不买了」确实该留空，但还有一类是**勾漏了、买了忘勾**。彻底消失会让用户困惑"我明明买了怎么没有"。折叠一行、点一下加回来，成本几乎为零。

**S3 · 「家里还有的」是这个改动真正的价值。**
购物清单里永远不会有：冰箱里的鸡蛋、酱油、上周剩的半颗白菜。而这些恰恰决定了"能做什么菜"。**只带勾选项进去，推荐会偏少偏怪 —— 这是这个功能会不会被用第二次的分水岭。**

### 数据

新增库存表（字段名请映射到现有约定）：

```ts
type PantryItem = {
  id: string
  name: string
  lastConfirmedAt: number    // 最近一次被"盘"到的时间
  origin: 'leftover' | 'manual'
}
```

清单项建议补一个字段：

```ts
checkedAt?: number   // 勾选时间。用于"这次买的"判定和后续衰减
```

### 状态流转

**提交盘一盘时**，写入库存：
```
pantry ← 这次买的（未删除的）
      + 还买了别的
      + 家里还有的（本次仍勾选的）
每一项 lastConfirmedAt = now
本次取消勾选的「家里还有的」→ 从 pantry 移除
```

**再次打开盘一盘时**，「家里还有的」按新鲜度分两区：

| 距上次确认 | 处理 |
|---|---|
| ≤ 7 天 | 活跃区，默认勾选 |
| > 7 天 | 折叠成「可能吃完了（N）」，默认不勾 |

**永不自动删除。** 折叠区提供一键清空。自动删掉用户没同意删的东西，比留着过期数据更糟。

### 三个必须避开的陷阱

1. **不要数量。** 只要"有 / 没有"。一旦引入 2 根玉米、剩 1.5 根，就变成需要精确维护的库存系统，而用户不会每次吃完回来减。
2. **不要自动扣减。** 做完一道菜不要自动把食材从库存划掉 —— 猜错一次就是错误数据，而用户不会去修。
3. **维护成本一旦超过"重新打一遍"，功能就死了。** 每加一个字段先问：用户会不会维护它。

### 不要动的
盘一盘之后**不清空购物清单的勾选状态**。用户可能还要回去看自己买了什么。两份状态独立。

## 四、为什么「家里还有的」值得单独做

前面的市场分析里，这个产品最大的隐形竞品是通用 AI —— 用户可以直接问 ChatGPT「我有排骨冬瓜做什么」。

**GPT 不记得你上周买了什么。**

「家里还有的」是通用 AI 结构上给不了的东西，而且它随使用累积。这是这个产品少数几个真正有护城河的地方，比任何菜谱内容都硬。优先级应当高于任何内容功能。

---

## 五、怎么判断做对了

**不要看「盘一盘」的点击率。** 自动带入之后它必然会涨，涨了不说明任何事。

**看点完之后有没有真的进到某道菜。**

| 观察 | 结论 |
|---|---|
| 点击率↑ 进菜率↑ | 做对了 |
| 点击率↑ **进菜率持平** | **瓶颈从来不在打字，在推荐结果不够好。** 停下，去看推荐 |
| 二次使用时「家里还有的」被大量取消勾选 | 衰减窗口太长，7 天改 4 天 |
| 「家里还有的」几乎没人展开 | 默认折叠错了，或者位置不对 |

第二行是最重要的一行。如果出现，这三个改动虽然体验更顺，但没解决真问题。
